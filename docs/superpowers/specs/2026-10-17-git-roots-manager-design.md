# git-roots-manager — дизайн плагина для PhpStorm

- **Дата:** 2026-10-17
- **Статус:** черновик на согласование
- **Целевая IDE:** PhpStorm 2026.2.3 (build PS-262.10968.76, платформа 262)

## Замысел

В монорепозитории PhpStorm цепляет десятки вложенных git-репозиториев: панель
VCS, индексация и коммиты работают со всеми сразу, и приходится вручную ходить
в Settings → Version Control → Directory Mappings, чтобы отключать лишние.

Плагин даёт иконку-виджет в статус-баре IDE (аналогично GistsSnippet): клик
открывает модальное окно со списком обнаруженных git-репозиториев проекта.
Клик по чекбоксу мгновенно включает или выключает отслеживание репозитория —
без кнопки Apply.

## Цели

- Виджет в статус-баре, видимый в проектах с git; клик открывает диалог.
- Диалог: список git-корней проекта (зарегистрированные маппинги + обнаруженные
  вложенные `.git`), у каждого — чекбокс «отслеживать».
- Чекбокс применяет изменение сразу, в момент клика.
- Выключенный корень **не возвращается** после пере-детекции корней и после
  перезапуска IDE.
- Состояние персистентно per-project.
- Установка локально: `Install Plugin from Disk` (без Marketplace).

## Не-цели

- Профили/наборы репозиториев (осознанно отложено пользователем).
- Публикация в JetBrains Marketplace.
- Git-операции (commit/push/fetch и т.п.).
- Поддержка других VCS как отдельная задача: код маппингов платформенно
  VCS-агностичен, но проектируем и тестируем только на git.
- Пресеты/автоприменение при открытии проекта.

## Анти-цели (провал, даже если «работает»)

- После «выключения» PhpStorm снова подцепляет репозиторий.
- Переключение требует перезапуска IDE или пересканирования руками.
- Плагин пишет что-либо за пределами настроек проекта (`.idea`) и собственного
  локального состояния.
- Диалог тормозит или зависает UI при большом числе репозиториев.

## Архитектура

### Компоненты

1. **Виджет статус-бара** — `StatusBarWidgetFactory` + кастомный `StatusBarWidget`
   (EP `com.intellij.statusBarWidgetFactory`). Иконка; клик открывает диалог.
   Доступность виджета — в проектах, где есть хоть один git-маппинг или
   обнаруженный `.git`. Точные сигнатуры презентации с обработчиком клика
   сверить по исходникам платформы 262 (кандидат — `IconPresentation` с
   click-consumer).
2. **Диалог** — `DialogWrapper` + Kotlin UI DSL. Строки: относительный путь
   репозитория + чекбокс текущего состояния. Сортировка по пути. Обработка
   клика — на EDT, применяется мгновенно, затем строка обновляется по факту
   (источник истины — модель, а не визуальное состояние чекбокса).
3. **Модель корней (`RootStore`)**
   - Список в диалоге = объединение двух источников:
     - зарегистрированные маппинги — `ProjectLevelVcsManager.getDirectoryMappings()`;
     - собственный список выключенных корней плагина (см. п. 5).
   - Файловую систему плагин сам **не сканирует**: обнаружение репозиториев —
     задача платформы (VCS root detection). «Свежие» репозитории попадают в
     диалог после того, как платформа их детектирует и зарегистрирует; при
     открытии диалога плагин может запросить у платформы повторное обнаружение
     (API рескана — сверить в исходниках 262).
   - Отклонённая альтернатива: собственный рекурсивный скан `.git` под корнем
     проекта — дублирует готовый механизм платформы, добавляет тормоза на
     больших монорепо и вторую реализацию той же логики.
   - Известное ограничение MVP: корни, которые платформа обнаружила, но которые
     ещё не зарегистрированы (ожидают подтверждения детекции), в диалоге не
     показываются — они появляются после регистрации. Возможность их показа —
     вопрос рекогносцировки API (план, Task 1), не обещание.
   - **Режим `<Project>` (маппинг по умолчанию, directory = "").** Проект
     трекает все обнаруженные корни через единственную запись. Тогда:
     - список в диалоге = результат `VcsRootDetector.detect()` (все корни,
       tracked = true) + собственный список выключенных; строка `<Project>`
       показывается заблокированной;
     - выключение корня «разворачивает» дефолт: плагин строит явные маппинги
       из всех обнаруженных корней, кроме выключаемых (уже явные маппинги
       сохраняются, дубли исключаются), и убирает запись `<Project>`;
       дальнейшая работа — обычная модель;
     - включение в дефолт-режиме разворота не требует: дефолт уже трекает
       всё, достаточно убрать корень из выключенных и игнор-листа;
     - `detect()` сканирует ФС — вызывается только вне EDT; диалог читает
       список и применяет тоглы асинхронно, с колбэком на перерисовку.
4. **Переключение**
   - Включить → добавить/восстановить directory mapping через
     `ProjectLevelVcsManager.setDirectoryMappings()` (стабильный API).
   - Выключить → убрать mapping **и** занести корень в игнор-лист детектора,
     иначе платформа пере-детектит его и покажет уведомление/вернёт в проект.
5. **Собственное персистентное состояние** — `PersistentStateComponent`
   (per-project, в workspace-области): список выключенных корней.
   - Первично игнорирование делается платформенным API игнор-листа
     (кандидаты: `VcsRootProblemNotifier` / `VcsConfiguration` — **проверить
     точный API в исходниках 262**, наугад не использовать).
   - Гарантированный fallback, работающий даже если API игнора недоступен или
     изменился: при открытии проекта и после VCS-скана плагин сверяет своё
     состояние с текущими маппингами и повторно убирает «выключенные».
6. **Инициализация** — легковесный `ProjectActivity` (Kotlin coroutines):
   при открытии проекта сверить состояние и пере-применить маппинги.

### Данные и хранение

- Включённые корни — сами directory mappings в `.idea/vcs.xml` (механизм
  платформы, плагин его не изобретает).
- Выключенные корни — локальное состояние плагина per-project (workspace-область,
  обычно не коммитится).
- Проверено на целевом монорепо `logikamoloka-dev-env`: `.idea/` целиком в
  `.gitignore`, vcs.xml не под гитом — изменения маппингов остаются локальными
  и коллег не затрагивают. Для других проектов поведение зависит от их
  `.gitignore`; специальной обработки в MVP нет.

## API к проверке при реализации

Следующее сверяется с исходниками/SDK платформы 262 до написания кода —
в дизайне зафиксированы намерения, а не гарантированные сигнатуры:

- обработчик клика виджета статус-бара (презентация и её метод клика);
- платформенный API игнор-листа VCS-корней;
- API повторного обнаружения VCS-корней по запросу (для «свежих» репозиториев
  при открытии диалога);
- уведомление UI об изменении маппингов (достаточно ли `setDirectoryMappings`,
  или нужен дополнительный rescan — например, через `VcsRootScanner`).

## Критерии приёмки

1. В монорепо виджет виден; клик открывает диалог со всеми git-корнями,
   включая вложенные.
2. Снятие чекбокса: репозиторий мгновенно исчезает из отслеживания (панель
   Changes/Commit), в том числе после ручного VCS-обновления.
3. Перезапуск PhpStorm: выключенные остаются выключенными, уведомлений о
   «незарегистрированных корнях» нет.
4. Включение чекбокса: репозиторий мгновенно возвращается в отслеживание.
5. Проект без вложенных репозиториев: диалог показывает корневой маппинг,
   ошибок нет.
6. `buildPlugin` → zip → «Install Plugin from Disk» в PhpStorm 2026.2.3 —
   плагин включается и работает.

## Тесты

- Юнит-тест на diff-логику маппингов (включить/выключить → целевой список
  маппингов) — это значимая логика, остальное по правилам пользователя
  проверяется ручным смоуком по чек-листу критериев приёмки.
- Тестовую инфраструктуру ради мелочей не создавать.
